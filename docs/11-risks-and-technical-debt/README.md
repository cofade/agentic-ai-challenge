# 11. Risks and Technical Debt

Known risks, deliberate trade-offs, and items deferred to future iterations. Updated whenever a decision creates a known limitation.

## Known limitations

- **BM25 fake-hit vote inflation in hybrid RAG.** On an out-of-vocabulary query, `BM25` returns top-`k` chunks with `score == 0.0` in original corpus order. `HybridRetriever` folds those into RRF unfiltered, so they co-vote with any genuine embedding hits and can inflate the fused rank of an unrelated chunk. Documented in [ADR-006](../09-architecture-decisions/ADR-006-hybrid-rag.md) (negative-consequences section); pinned as a regression-watch test in `tests/unit/test_hybrid.py::test_bm25_oov_fake_hits_flow_through_unfiltered`. Mitigation (score-threshold filter on BM25 results before RRF) is deferred to issue #16 — the eval harness will quantify whether it actually regresses retrieval quality on the labelled set, and we don't want to hand-tune a threshold without that signal.
- **Retrieval is not version-aware.** The BM25 tokenizer (`src/wscad_triage/kb/retriever.py`) splits on Unicode `\w+`, so a version literal like `v7.3.2.16` shreds into the tokens `["v7", "3", "2", "16"]`. A query that names a version (e.g., "license activation in v7.3.2") therefore matches every release note that contains any of those numeric components, and the final ranking is decided by the surrounding lexical density — not by version semantics. `tests/unit/test_extended_corpus.py::test_version_string_tokenisation_is_dot_split` pins this tokenisation behaviour so the dependent retrieval test cannot silently start passing for a different reason. Genuine version-aware retrieval (metadata-conditioned filter on `KBChunk.metadata["version"]` before scoring) is future work; the Phase 3 supervisor or a Phase 4 ADR should claim it.
- **The all-or-nothing invariant is per-subcorpus, not project-wide.** `test_kb_corpus.py` enforces consistency of `synthetic_for_demo` across `kb/electrix_ai_release_notes/` only. Phase 3+ may add new sourced subcorpora (e.g., `kb/manuals/`, `kb/forum_posts/`); each will need its own consistency test, or the existing test should be parametrised over a registry of sourced subdirectories. The current per-directory hardcoding keeps the contract scoped and unambiguous, but it does not generalise without a refactor when the second sourced subcorpus lands.
- **Verifier groundedness threshold is not empirically grounded yet.** The 0.4 cutoff in [ADR-008](../09-architecture-decisions/ADR-008-groundedness-gate.md) is a defensible default ("one of three claims ungrounded" trips it; "one of five questionable" does not) but has no eval-set support. Phase 5's labelled ungrounded-trap tickets (#34) will revisit. Related: the verifier itself is an LLM and can hallucinate verdicts; layer-1 defences in `src/wscad_triage/agents/reason.py` (fabricated chunk_ids → ValueError; quote-not-in-chunk → ValueError) cap the worst-case escape, but a verifier that wrongly accepts an entailment can still let a subtle misread through.
- **Supervisor routing is deterministic in Phase 3.** [ADR-005](../09-architecture-decisions/ADR-005-supervisor-topology.md) ships LangGraph with two pure routing functions and a fixed 0.4 grounding threshold. If Phase 5 eval reveals the static thresholds underperform on edge cases (e.g. a ticket where the right call depends on classifier rationale rather than a boolean test), the swap-in is per-edge: replace one routing function's body with an LLM call. The graph topology and worker contracts stay put.
- **Confidence formula is live but weights are not eval-tuned.** `final_confidence = min(rubric_score, verifier_score)` on the solve path; `rubric_score` alone on the clarify path. The two rubric components (`retrieval_quality`, `metadata_completeness`) and their default weights (0.5/0.5, penalty 0.25) are defensible defaults, but no labelled eval set has been used to optimise them. Phase 5 (#34) will run a grid search over weight combinations against the held-out ticket set. Until then, the confidence bands (< 0.5 → clarify, 0.5–0.7 → caveated solution, > 0.7 → confident solution) are informational only — routing is decided by the LangGraph topology, not by the confidence value.
- **`langsmith` is in the transitive dependency set.** `langgraph 1.x` pulls `langsmith 0.8.x` transitively. The package is inert without `LANGSMITH_API_KEY` / `LANGCHAIN_TRACING_V2=true`, but a developer who happens to have those vars set in their shell would silently ship support-ticket text to `api.smith.langchain.com`. CI scrubs env vars (`tests/unit/conftest.py:_scrub_settings_env`); the live-API integration test does not. Phase 5 should decide whether to keep langgraph + audit transitive deps on each bump, or vendor a slimmer subset (e.g. graph-core only). Until then: do not set the LangSmith env vars when working with real customer tickets.
- **`eval/` is outside the mypy gate.** `mypy` is configured for `src/` only (`[tool.mypy] packages = ["wscad_triage"]`). Type annotations in `eval/metrics.py` and `eval/runner.py` are therefore decorative — a regression there would not be caught by pre-commit. Pulling `eval/` into the mypy target requires either adding `wscad_triage` to `mypy_path` (so eval can import it) or shipping a `py.typed` marker on the package. The annotations exist and are correct; the gate just does not read them. Tracked for resolution in Phase 6 or whenever the harness is promoted to a first-class quality-gated module.
- **Ollama tool-use fidelity is model-dependent.** `gpt-oss:20b` is the project's tested choice for the `OllamaBackend` (issue #55, ADR-004). Smaller open-weight models (`qwen2.5:7b`, `llama3.1:8b`, `mistral:7b`) have visibly worse tool-call reliability — they can emit malformed JSON `arguments`, missing required fields, or text alongside a half-formed tool call. The workers' Pydantic validation catches the malformed-arguments case (raises `ValidationError`) so the failure is loud rather than silent, but a quietly-wrong call can still slip through. Phase 5 (#34) adds a per-model fidelity benchmark over the labelled eval set. Until that lands, the README and ADR-004 list `gpt-oss:20b` as the only supported Ollama model; deviating is at the operator's risk.

## Deliberate non-goals (already decided)

- No UI / frontend (challenge brief: "Not Required").
- No model fine-tuning (brief: "Not Required").
- No external data sources at runtime — KB only.
- No coverage of legacy WSCAD product lines (SUITE, ELECTRIX non-AI, ELECTRIX ROCKET).
- No C# / .NET implementation (see ADR-001).

## Closed risks (resolved)

- **Phase 2 KB corpus was synthetic (issue #48, resolved).** The original live scrape returned `HTTP 403` (bot-protected); the corpus initially shipped as six hand-authored synthetic notes tagged `synthetic_for_demo: true`. Issue #48 performed the real-content swap: the release-notes page was downloaded as HTML and converted by a one-off script (not committed to the repo, per ADR-003) to produce 14 German-language Markdown files covering all ELECTRIX AI versions v7.3.0.16–v7.4.0.17, all tagged `synthetic_for_demo: false`. The `test_kb_corpus.py` consistency test guards the all-or-nothing invariant. A future improvement could add the English-language versions from the parallel release-notes URL for cross-lingual balance (tracked in ADR-009).

## Future work

- An evaluation pass with a held-out ticket set of 100+ items would let the rubric weights be tuned by gradient-free optimisation rather than by hand.
- Per-claim caching of grounding verdicts would reduce verifier latency on repeated KB chunks.
- A first-class production integration path (HTTP service or `Python.NET` host) is sketched in the README but not implemented.
